# Diagnosis Protocol — 诊断流程与证据规则

## 核心纪律

1. **只读**。诊断阶段不修改任何生产数据、不杀进程、不改 state。
2. **多证据**。任何结论至少两条独立证据（如"内存爆了"= 异常文件 + commit 读数）。
3. **区分"故障"与"证据不足"**。UNKNOWN 表示缺数据，不是坏消息，也不该
   拉低整体结论；但必须显式列出缺什么。
4. **不猜**。证据不足时说不确定，并给出"要确认什么、去哪看"。
5. **区分终态与在途**。done/recovered_success 是终态（永不重跑）；
   claimed/pending 是在途（可恢复）；failed 是终态但可显式重试。

## 诊断顺序（从外到内）

```
1. 宿主资源      commit/物理内存 → 决定"能不能继续跑"
2. 进程状态      进程表按 tag/run_dir 匹配 → 决定"有没有在跑、跑了几份"
3. 状态机        state.json 五态 → 决定"跑到哪了、是否完成"
4. 产物一致性    works/ 逐单元核对 → 决定"完成是不是真的"
5. 上游健康      llm_calls.jsonl 尾部 → 决定"是不是网络在烧任务"
6. 异常现场      logs/*.exception.json → 定位崩溃根因
```

**为什么这个顺序**：资源决定能不能动手（在 commit 耗尽时做任何恢复都是
火上浇油）；进程决定有没有并发冲突（双启动时改 state 会放大错乱）；
状态机是事实源；产物是"完成"的硬证据；上游决定要不要熔断；
异常现场只在需要根因时深入。

## 证据强度分级

| 强度 | 例子 | 用法 |
|---|---|---|
| **硬证据** | state.json 五态、磁盘产物、异常文件、commit 读数 | 可直接下结论 |
| **软证据** | Dashboard 面板数字、日志文本、进程名 | 需交叉验证 |
| **弱证据** | 用户印象、时间相关性、单一日志行 | 只能作线索 |

**Dashboard 是软证据**：它的 completed/活跃/待办是三个不同口径，历史上
多次造成误判（FM-06）。验收一律以 state.json + 磁盘为准。

## 常见误判与纠正

| 误判 | 纠正 |
|---|---|
| "pending==0 就是完成了" | 五数齐全才算（FM-07） |
| "生产太重把内存吃爆了" | 生产树仅 ~0.5GB，真凶在宿主（FM-01） |
| "/health 正常所以网关没问题" | /health 不发网络调用，要真实探测（FM-11） |
| "启动报 500 所以没起来" | 可能已起来，先查进程表（FM-08） |
| "读 state 报错所以数据坏了" | 可能只是 replace 瞬间，重试 ≥4 次（FM-10） |
| "failed 重跑一下就好了" | failed 是终态，需显式重试且先备份（R1） |
| "加 worker 就能更快" | 瓶颈是单元内 3 次串行调用（FM-12） |

## 输出格式

诊断报告（给人看）应包含：

```
结论：<级别> — <一句话>
证据：
  - <硬证据 1>
  - <硬证据 2>
判断：<对应 FM-xx 及理由>
建议动作：<具体命令或操作，标注是否需人工确认>
证据缺口：<缺什么，去哪补>
```

**不要**在证据不足时给"可能是 A 也可能是 B"的模糊结论——列出已排除的
和待确认的，比罗列可能性有用。

## 与 night-fiction-factory 的分工

| Skill | 职责 |
|---|---|
| `literary-incident-response` | 判断"出了什么事、为什么"（只读诊断） |
| `night-fiction-factory` | 执行"怎么恢复"（resume/stop/launch/watch） |

诊断完把动作交给 night-fiction-factory 执行，不要在本 Skill 里动手改数据。

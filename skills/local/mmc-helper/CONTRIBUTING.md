# 贡献指南

感谢你愿意改进 mmc-helper。

---

## 一、先理解设计前提

本 skill 的一切设计都服务于一个前提：**主导权在用户**。
因此，贡献时请守住三条：

1. **不削弱"留窗口"**——任何自动化都不应让用户失去在关键决策点插话的机会；
2. **不把流程变成形式**——新增步骤必须有它解决的问题，否则不如不加；
3. **不写死场景**——规则表述保持通用，避免绑定某一次竞赛或某一类题目。

---

## 二、可以贡献什么

| 类型 | 说明 | 放哪里 |
|---|---|---|
| 新增已知坑 | 一个常见缺陷 + **如何检出** | `references/known_pitfalls.md` |
| 新增写作范式 | "原稿 → 问题 → 改法"三列 | `references/style_patterns.md` |
| 新增协议 | 一类反复出现的问题的固定处理流程 | `protocols/` |
| 新增角色 | 职责清晰、边界可写清 | `agents/` |
| 改进模板 | 更易套用、更少留白 | `templates/` |
| 修正错误 | 表述矛盾、链接失效、示例过时 | 对应文件 |
| 补充论文库笔记 | 公开获奖论文的阅读笔记（只写结构与写法，不搬内容与结论） | `paper-library/notes/` |
| 翻译 | 其他语言的 README | `README.<lang>.md` |

---

## 三、贡献约定

### 1. 保持文档分层

本仓库的文档分四层，新增内容请归入正确的一层：

| 层 | 回答的问题 |
|---|---|
| `SKILL.md` | 触发什么、总流程是什么 |
| `protocols/` | 遇到某类问题按什么规矩办 |
| `agents/` | 谁来做、边界在哪 |
| `references/` `templates/` | 依据是什么、怎么套用 |

### 2. 一个文件说清一件事

不要把一个文档写成变更日志。**当前有效的版本在前，历史移出**。

### 3. 例子要通用

举例时使用**领域中性的表达**，不要绑定具体赛事、题目或数据。

### 4. 改动前先看结构

- 目录结构见 `INDEX.md`；
- 角色与协议的对应关系见 `agents/README.md`。

### 5. 提交信息

建议格式：

```
<范围>: <一句话说明>

例如：
protocols: 补充交接文档的长度上限说明
references: 新增一条"绘图数据粒度与结果文件不一致"的坑
```

---

## 四、不建议的改动

- 在 `SKILL.md` 里堆砌细节（细节应下沉到 `protocols/` 或 `references/`）；
- 新增与既有协议重复的流程；
- 引入与"用户主导"相冲突的自动化；
- 在示例中包含真实竞赛的题目、数据或结论（`examples/` 一律用虚构题目）；
- 把笔记写成变更日志（`paper-library/` 的笔记例外：它们记录的是**对公开论文的阅读结论**，
  可以引用其公开的题名与结果数值，但仍不得搬用其模型与结论）。

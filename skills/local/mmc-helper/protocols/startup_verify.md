# 协议 · 启动自检

> 解决的核心问题：**新会话接手时，文档记录的与实际文件不一致，而没人去验证**。
> 智能体凭文档印象开工，一路错到底。
>
> **触发时机**：① **新会话开始、接手既有项目时**（必做）；② 上下文被压缩后恢复工作时；
> ③ 多个窗口并行推进、怀疑状态已发散时；④ 收尾前做最终核对时。

---

## 一、原则

**新会话的第一步不是"读文档"，而是"跑校验"。**
文档是人写的，会过期；文件是客观的，可校验。

---

## 二、校验流程

```
1. 读 state.json（权威状态）
2. 逐条校验：
   a. artifacts[] 中每个产物的路径是否存在、时间戳是否与记录一致
   b. 记录中的关键参数是否与结果文件/程序实际使用的参数一致
   c. superseded[] 中标记为作废的内容，是否确实已从正文/文档中移除
   d. open_questions[] 是否仍待用户拍板
3. 输出差异报告
4. 差异为 0 → 开工；有差异 → 先报告用户，确认后再开工
```

---

## 三、`state.json` 需要承载的信息（权威状态）

| 字段 | 用途 |
|---|---|
| `phase` / `current_role` / `interaction_mode` | 流程位置 |
| **`artifacts[]`** | 每个产物的**路径 + 时间戳 + 摘要**（哪一问的、什么角色产出、是否定稿） |
| **`active_params`** | 当前生效的**全部参数与设定**（含标定窗、评价窗） |
| **`superseded[]`** | 已作废的设定 / 数字 / 结论 **+ 替代者** |
| **`open_questions[]`** | 待用户拍板的事项 |
| `known_issues[]` | 已确认的缺陷（供审核手交叉检查） |

---

## 四、差异报告模板

```markdown
# 启动自检报告（YYYY-MM-DD HH:MM）

## 一致项
- N 项全部一致

## 差异项
| # | 记录内容 | 实际内容 | 影响 | 建议 |
|---|---|---|---|---|

## 结论
- [ ] 差异为 0，可开工
- [ ] 存在差异，请用户确认后开工
```

---

## 五、与交接协议的配合

- 交接文档（`protocols/handoff_protocol.md`）负责**人可读的现状摘要**；
- `state.json` 负责**机器可校验的权威状态**；
- 两者冲突时，**以实际文件为准**，并把文档改正。

---

## 六、为什么必须做

- 长会话中，**上下文压缩会丢掉状态**，文档是唯一残留，但文档可能没跟上；
- 多会话并行时，**不同窗口会改到同一批文件**，状态极易发散；
- 用户被反复追问"现在到哪一步了"，本身就是效率损失。

**把校验自动化，是让协作可预期的前提。**
